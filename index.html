A chain is not a row of blocks.
It’s a row of fingerprints.

Every block carries a copy of the previous block’s hash. That single detail is what makes the history tamper-evident — and you can prove it to yourself in about ten seconds. Edit the data in the first block below and watch what happens to the two after it.

Chapter 01 — anatomy

What is actually inside a block

Strip away the jargon and a block is four fields. Three of them are ordinary. The fourth is the one that does all the work.

01

Data

Whatever the block is recording — payments, votes, a document hash. On this site it’s a one-line transaction so you can type into it and see the effect.

02

Nonce

A number with no meaning of its own. Its only job is to be changed over and over until the block’s hash comes out in an acceptable shape. That searching is “mining”.

03

Previous hash

The link. A copy of the hash of the block before this one. Not a pointer or an ID that could be quietly re-aimed — a fingerprint of that block’s exact contents.

04

This block’s hash

SHA-256 of all three fields above, combined. Because the previous hash is one of the inputs, this value depends on the entire history behind it.

The commitment

Each block on this site hashes exactly this string, and the simulator prints it under every block so you can see it change:

index=2|data=Grace pays Linus 1 ETH|prev=a3f9…|nonce=0

Chapter 02 — the cascade

Why one edit breaks everything after it

A hash function has a property called the avalanche effect. Change one character of the input and the output doesn’t shift slightly — it becomes a completely unrelated 64-character string. There is no partial credit and no near-miss.

So picture someone quietly editing block 1 to pay themselves more. Block 1’s data changed, therefore block 1’s hash changed. But block 2 is still storing the old hash in its “previous hash” field. The two no longer agree, and anyone checking can see it instantly.

Worse for the forger: fixing block 2 to store the new hash changes block 2’s own hash, which breaks block 3. And so on, to the end of the chain. Rewriting one line of history means redoing every block that came after it — faster than everyone else is adding new ones.

Try it

Scroll back up, change a single character in block 1, and watch blocks 2 and 3 turn red without being touched. Nobody validated anything. The arithmetic simply stopped agreeing.

Chapter 03 — consequences

Three things this buys you

Tamper-evident, not tamper-proof

Nothing stops someone editing their own copy. The point is that everyone else can tell immediately, because their copy’s hashes won’t match. Detection, not prevention.

History gets more expensive to change over time

Rewriting the most recent block costs one block of work. Rewriting a block from a year ago costs a year of work. Depth is security.

No trusted referee required

You don’t have to trust the person handing you the chain. You can recompute every hash yourself and check. That is the actual innovation.

Chapter 04 — the same thing, for real

Now look at a block worth billions

Everything above is a model running in your browser. Use Connect wallet in the top bar and this site will pull the newest real block from whichever network your wallet is on, and draw it in exactly the same layout as the ones you have been editing.

Look at where the fields land. What Ethereum calls parentHash sits in the same slot as the prev field on the cards above — because it is the same idea. That block is holding the fingerprint of the block before it, for the same reason yours were. Nothing about the mechanism changes when the stakes do.

What this site can and cannot do

The connection is read-only. This page calls eth_requestAccounts to ask for an address, eth_getBalance to read a balance, and eth_getBlockByNumber to fetch that header. It never requests a signature, never builds a transaction, and cannot see your private key — the maths does not run in that direction. That is the public-versus-private-key distinction from the Concepts page, working in front of you.
